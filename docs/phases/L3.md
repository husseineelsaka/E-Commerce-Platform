# L3 — G2 (S27)

## Goal

The Kafka Saga by choreography (ADD §5): transactional outbox publishers in Order, Inventory, and Payment; stock reservation and release (FR-07); payment from events with Resilience4j Retry and CircuitBreaker (FR-08, FR-09); order outcomes `CONFIRMED` / `CANCELLED` with compensation; notifications with retries and a dead-letter topic (FR-11); idempotent consumers and DLTs (NFR-10); orders survive a Payment outage (NFR-01); no orphaned reservation after cancellation (NFR-05).

## Event flow

```text
Order    --OrderPlaced-------------> order-events     --> Inventory (reserve), Notification (ignored)
Inventory--InventoryReserved-------> inventory-events --> Payment (charge), Order (ignored)
Inventory--InventoryReservationFailed-> inventory-events --> Order (CANCELLED)
Payment  --PaymentCompleted--------> payment-events   --> Order (CONFIRMED)
Payment  --PaymentFailed-----------> payment-events   --> Inventory (release), Order (CANCELLED)
Inventory--InventoryReleased-------> inventory-events    (audit only)
Order    --OrderConfirmed / OrderCancelled -> order-events --> Notification
```

Every event is keyed by `orderId`, so one order's events stay in order on one partition.

## Decisions

**DECISION:** Each producing service has its own `outbox_event` table and a polling publisher (every 500 ms) that sends rows with `FOR UPDATE SKIP LOCKED`, synchronously, then marks them published.
**OPTIONS CONSIDERED:** Direct publish after commit; transactional outbox with a polling publisher; change-data-capture.
**REASON:** The state change and its event commit together, so there is no window where the database changed but no event was sent (ADD §5). SKIP LOCKED keeps several instances from sending the same row.
**TRADE-OFF:** Up to one poll interval of delay; a crash after send but before commit re-sends the row, which every consumer tolerates.
**WHAT WOULD MAKE US REVISIT:** Poll delay showing in the L5 order latency.

**DECISION:** Every consumer records the `eventId` in `processed_event` (`INSERT … ON CONFLICT DO NOTHING`) in the same transaction as its state change and outbound event; Order changes state only from `PENDING` (`UPDATE … WHERE status = 'PENDING'`); Payment charges an order at most once (`order_id UNIQUE`, key = `orderId`).
**OPTIONS CONSIDERED:** Kafka exactly-once transactions; idempotent consumers.
**REASON:** Kafka transactions do not cover our database writes; at-least-once plus idempotent consumers is the handbook default (NFR-10) and is testable.
**TRADE-OFF:** One extra table and insert per consumed event.
**WHAT WOULD MAKE US REVISIT:** `processed_event` growth slowing inserts — then a cleanup job.

**DECISION:** Inventory reserves all lines of an order or none: it locks the order's stock rows in product-id order (`SELECT … FOR UPDATE`), checks them, and only then changes them.
**OPTIONS CONSIDERED:** Per-line conditional updates with rollback; lock, check, then update.
**REASON:** No partial reservation is ever visible, a failure needs no undo, and the fixed lock order avoids deadlocks between concurrent orders.
**TRADE-OFF:** Concurrent orders for the same product wait for each other's short transaction.
**WHAT WOULD MAKE US REVISIT:** Lock waits showing up in the L5 order load test.

**DECISION:** The Saga charge runs inside Resilience4j Retry (3 attempts, 200 ms) and CircuitBreaker; exhausted retries or an open circuit store the payment as `FAILED` and publish `PaymentFailed`.
**OPTIONS CONSIDERED:** Fail on the first decline; retry forever; bounded retry then compensation.
**REASON:** A transient decline does not cancel an order, and a lasting failure ends in compensation instead of an order stuck in `PENDING` (PLAN Saga outcomes).
**TRADE-OFF:** A failing order takes about 0.4 s longer to cancel.
**WHAT WOULD MAKE US REVISIT:** A real payment provider with its own retry semantics.

**DECISION:** Business services park a record on `<topic>.DLT` after 3 retries (`DefaultErrorHandler`); Notification uses `@RetryableTopic` (4 attempts, 1 s doubling) with `dltTopicSuffix = ".DLT"`.
**OPTIONS CONSIDERED:** Spring Kafka's default `-dlt` suffix; `.DLT`.
**REASON:** The ADD and backlog name the DLT `order-events.DLT`; the Spring default would have created `order-events-dlt` (ADD §6 F5).
**TRADE-OFF:** One explicit setting to keep.
**WHAT WOULD MAKE US REVISIT:** A platform-wide DLT naming standard.

**DECISION:** Notification has no database and therefore no deduplication.
**OPTIONS CONSIDERED:** Add a database for dedup; accept rare duplicates.
**REASON:** The handbook gives Notification no store; Order publishes each outcome once, so a duplicate only follows an outbox re-send after a crash.
**TRADE-OFF:** In that case a customer can receive the same notice twice.
**WHAT WOULD MAKE US REVISIT:** Notifications that cost money or must be exactly once.

## Startup commands

As in `docs/phases/L2.md`, plus:

```sh
mvn -pl services/notification-service spring-boot:run
```

All services read `KAFKA_BOOTSTRAP_SERVERS` (default `localhost:9092`, the Compose broker). Demo switches: `PAYMENT_FAILURE_RATE=1.0` for payment-service (every charge declines), `NOTIFICATION_FAIL=true` for notification-service (every send fails → DLT).

## Evidence

Recorded 2026-10-01 with all eight services running, the Compose Kafka broker, PostgreSQL, and Keycloak; orders placed through the Gateway with a real `customer-test` token.

- **Happy path:** order for 2 × product 5 → `CONFIRMED` about 1 s after it was placed. Stock 1000/0 → 998 available / 2 reserved; reservation `RESERVED qty 2`; payment `COMPLETED 59.98`; outbox rows `OrderPlaced`, `InventoryReserved`, `PaymentCompleted`, `OrderConfirmed`, all published; notification log: `Your order 13e29a24-… is confirmed.`
- **Payment failure (compensation):** payment-service restarted with `PAYMENT_FAILURE_RATE=1.0`; order for 3 × product 6 → `CANCELLED` within about 1 s. Payment `FAILED`; reservation `RELEASED qty 3`; stock back to 1000 available / 0 reserved; **0 `RESERVED` rows left** for the order (NFR-05); events `OrderPlaced`, `InventoryReserved`, `PaymentFailed`, `InventoryReleased`, `OrderCancelled`; notification: `Your order 058e9d84-… was cancelled: Payment declined.`
- **Payment outage (NFR-01):** payment-service stopped; order for product 7 stayed `PENDING` after 5, 15, and 25 s, with one `InventoryReserved` record waiting for the `payment-service` consumer group on `inventory-events`. After payment-service restarted, the order reached `CONFIRMED` about 4 s after it reported healthy; payment `COMPLETED 12.50`; confirmation sent; consumer lag back to 0 on all partitions.
- `mvn -B clean verify` passed on every story branch locally and in GitHub Actions.
