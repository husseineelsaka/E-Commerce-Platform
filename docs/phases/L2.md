## Decisions

**DECISION:** Order reads each item's price from Product and checks stock with Inventory before saving, then writes the order, its items, and the `OrderPlaced` outbox row in one local transaction.
**OPTIONS CONSIDERED:** Client-supplied prices; prices from Inventory; prices from Product (ADD §3.4).
**REASON:** Product owns prices; freezing `unit_price` keeps the order stable when the catalogue changes. Remote calls stay outside the transaction (AGENTS.md).
**TRADE-OFF:** A second synchronous dependency on the order path, and the stock check can race with other orders until L3 reserves stock.
**WHAT WOULD MAKE US REVISIT:** Order P95 near 800 ms because of the extra call.

**DECISION:** Both Order calls use Resilience4j CircuitBreaker, Retry (2 attempts), Bulkhead (20), and TimeLimiter (500 ms), configured in order-service's own `application.yml`; a Product 404 is neither retried nor counted by the breaker.
**OPTIONS CONSIDERED:** Settings in `config-repo`; settings in the service.
**REASON:** These are application behaviour, and tests run without Config Server — in `config-repo` the tests silently used Resilience4j defaults. An unknown product is a client error; counting it would let one bad id open the breaker for everyone.
**TRADE-OFF:** Changing a timeout needs a new build instead of a config change.
**WHAT WOULD MAKE US REVISIT:** Tuning the values per environment.

**DECISION:** Payment idempotency relies on the PostgreSQL `UNIQUE` constraints on `idempotency_key` and `order_id`; the payment row is inserted before the charge.
**OPTIONS CONSIDERED:** In-memory locks; a separate idempotency table; database constraints.
**REASON:** Constraints hold across concurrent requests and instances; inserting first means a losing duplicate fails on the constraint without charging.
**TRADE-OFF:** A lost race surfaces as a constraint exception that the service translates into the stored payment (same key) or 409 (other key).
**WHAT WOULD MAKE US REVISIT:** A real payment provider with its own idempotency keys.

**DECISION:** Every resource server resolves the Keycloak issuer lazily (`SupplierJwtDecoder`), and test profiles point the issuer at an unreachable address.
**OPTIONS CONSIDERED:** Eager `NimbusJwtDecoder.withIssuerLocation(...).build()`; lazy resolution.
**REASON:** The eager decoder contacted Keycloak at startup; CI has no Keycloak, so integration tests could not start (fixed in #11). A local Keycloak had hidden the problem.
**TRADE-OFF:** A wrong issuer is reported on the first request instead of at startup.
**WHAT WOULD MAKE US REVISIT:** A requirement to fail fast at startup when Keycloak is misconfigured.

**DECISION:** Inventory seeds 1000 units for demo products 1–19 and 0 for product 20.
**OPTIONS CONSIDERED:** A few units per product; a large stock.
**REASON:** The L5 k6 order load (20 VUs) would otherwise run out of stock within seconds; product 20 keeps the out-of-stock demo.
**TRADE-OFF:** Demo data in a migration.
**WHAT WOULD MAKE US REVISIT:** A separate seed mechanism for non-demo environments.

## Startup commands

As in `docs/phases/L1.md`, plus, in separate terminals with the variables from `deployment/docker/.env` exported:

```sh
mvn -pl services/inventory-service spring-boot:run  # needs INVENTORY_DB_PASSWORD
mvn -pl services/payment-service spring-boot:run    # needs PAYMENT_DB_PASSWORD
mvn -pl services/order-service spring-boot:run      # needs ORDER_DB_PASSWORD and ORDER_CLIENT_SECRET
```

Set `<SERVICE>_DB_PORT` when `POSTGRES_HOST_PORT` is not 5432.

## Evidence

Recorded 2026-10-01, JDK 21, Docker Compose infrastructure, Keycloak 26.3. Every story branch passed `mvn -B clean verify` locally and in GitHub Actions.

- **Payment** (real `payment-operator` token): first `POST` → 201 `COMPLETED`; same key and body → 200 with the same `paymentId`; same key, amount 50.00 → 422; other key, same order → 409; `order-service` token → 401 (no `payment-service` audience); one row in `payment_db`; refund → 200 `REFUNDED`, again → 409.
- **Order through the Gateway** (Gateway → order-service → product-service and inventory-service via Eureka): customer order of 2 × product 1 and 1 × product 3 → 201 `PENDING`; `GET` shows `totalAmount 208.98` with unit prices 79.99 and 49.00 from Product; `order_db.outbox_event` holds `OrderPlaced total=208.98 published=null`; product 20 → 409; product 999 → 400; admin `POST`/`GET` order → 403/403; admin `GET /api/v1/inventory/1` → `{"productId":1,"available":1000,"reserved":0}`; after admin `PUT /api/v1/inventory/20` the customer's order for product 20 → 201; customer list shows only own orders.
- **Resilience:** with inventory-service stopped, seven orders → 503 each; 1.13 s and 1.16 s for the first two, then 0.09–0.11 s once the circuit opened; no order saved; `resilience4j_circuitbreaker_state{name="inventory",state="open"} 1.0`.
