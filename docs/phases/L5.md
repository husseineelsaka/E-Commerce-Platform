## Decisions

**DECISION:** Each outbox row stores the W3C `traceparent` of the transaction that wrote it, and the relay publishes the event inside that trace.
**OPTIONS CONSIDERED:** Publish from the poller with no parent; propagate only when publishing directly from the request; store the trace context with the row.
**REASON:** The outbox poller runs on its own schedule, so without the stored context every saga event would start a new trace. With it, one order is one trace: Gateway → Order → Product/Inventory over HTTP → `order-events` → Inventory → `inventory-events` → Payment → `payment-events` → Order and Notification.
**TRADE-OFF:** One extra column per outbox table, and a span for each outbox publish.
**WHAT WOULD MAKE US REVISIT:** Moving to change-data capture (Debezium), which carries headers itself.

**DECISION:** Spring Security observations are disabled (`management.observations.enable.spring.security: false`).
**OPTIONS CONSIDERED:** Keep them at 100 % sampling; lower the sampling rate; disable only the security observations.
**REASON:** They produced 9 of the 12 spans of every product read and were the largest CPU cost in the Gateway profile. Without them, Gateway CPU per request falls 27 % and P95 at 800 req/s falls from 518 ms to 18.8 ms. Requests, Feign calls, and Kafka messages are still traced.
**TRADE-OFF:** A trace no longer shows how long authentication and authorization took. Security failures still appear as 401/403 on the request span and in the logs.
**WHAT WOULD MAKE US REVISIT:** A security latency problem that needs filter-level timing.

**DECISION:** The Gateway's rate limiter uses its token-bucket script read once into a static script source.
**OPTIONS CONSIDERED:** Keep the auto-configured script; load the script once.
**REASON:** The auto-configured script checks the Lua file's last-modified time inside the jar before every Redis call. That was 5.2 % of Gateway CPU, plus file access on the event-loop threads.
**TRADE-OFF:** We construct `RedisRateLimiter` ourselves instead of using the auto-configured bean.
**WHAT WOULD MAKE US REVISIT:** A Spring Cloud Gateway release that caches the script itself.

**DECISION:** Load and stress runs go through the Gateway from a k6 container on the Compose network. Stress runs raise the anonymous rate limit through `GATEWAY_ANON_REPLENISH_RATE` / `GATEWAY_ANON_BURST`.
**OPTIONS CONSIDERED:** Call services directly; run k6 on the host; stress through the normal limits.
**REASON:** The Gateway is the only public entry point, so it must be measured. Stressing through the default limits would only measure 429 responses.
**TRADE-OFF:** k6 shares the laptop's CPU with the platform, so latency at saturation is noisy. The report therefore also uses CPU per request.
**WHAT WOULD MAKE US REVISIT:** A separate load-generator machine.

## Commands

```sh
# Platform (only the Gateway on http://localhost:8080; Zipkin :9411, Prometheus :9090, Grafana :3000)
docker compose -f deployment/docker/docker-compose.yml --env-file deployment/docker/.env up -d --build --wait

# k6 (see k6/README.md); stress with the anonymous limit raised
docker run --rm --network docker_default -v "$PWD/k6:/scripts" -e BASE_URL=http://api-gateway:8080 grafana/k6:1.3.0 run /scripts/load-products.js
GATEWAY_ANON_REPLENISH_RATE=5000 GATEWAY_ANON_BURST=10000 \
  docker compose -f deployment/docker/docker-compose.yml --env-file deployment/docker/.env up -d api-gateway
docker run --rm --network docker_default -v "$PWD/k6:/scripts" -e BASE_URL=http://api-gateway:8080 -e PEAK=800 -e MAX_VUS=300 grafana/k6:1.3.0 run /scripts/stress-products.js
```

## Evidence

- **Trace across HTTP and Kafka:**
  - One order (`c6db5697…`, CONFIRMED) is one trace (`6abf8b16…`) with 23 spans across all six applications: api-gateway 2, order 9, product 1, inventory 6, payment 3, notification 2.
  - The `traceparent` stored with its `OrderPlaced` outbox row has the same trace id.
  - The notification JSON log line for that order carries `"traceId":"6abf8b1699e6fd792b330416f91fb483"`.
- **Grafana:**
  - The "E-Commerce Platform" dashboard is provisioned with 8 panels: req/s, P95 by service, payment-service consumer lag, Gateway status codes, circuit breakers, Kafka lag, JVM heap, and 5xx.
  - The lag panel queries `kafka_consumer_fetch_manager_records_lag_max{application="payment-service"}`.
  - Prometheus scrapes all 8 applications.
- **k6:**
  - Smoke: 108/108 checks.
  - Product load: P95 8.1 ms at 75 req/s, 0 % errors.
  - Order load at 20 VUs: P95 61.6 ms, 0 % errors.
  - Stress up to 800 req/s: P95 18.8 ms at the top stage, 0 errors, 0 dropped iterations.
- **Bottleneck:**
  - Before the fix, the Gateway's server P95 was 458 ms against 28 ms in product-service at 800 req/s. A JFR profile pointed to security observations and the per-request script check.
  - After the fix: Gateway CPU per request 4.23 → 3.08 ms, stress P95 at 800 req/s 518 → 18.8 ms.
  - Full data, method, and limitations are in [`docs/PERFORMANCE-REPORT.md`](../PERFORMANCE-REPORT.md).
