## Decisions

**DECISION:** The Gateway replaces the user's bearer token with its own `gateway-service` Client Credentials token and passes the user as `X-User-Id` / `X-User-Roles`, after stripping any client-supplied `X-User-*` header.
**OPTIONS CONSIDERED:** Forward the user's JWT to every service; Client Credentials token plus Gateway-injected identity headers.
**REASON:** Each service can check exactly which client called it (`azp`) and for which audience; a stolen user token cannot call internal endpoints.
**TRADE-OFF:** Services see the user only through headers, so header stripping is tested (`GatewaySecurityTest.stripsClientSuppliedIdentityHeaders`) and services trust the headers only from `gateway-service`.
**WHAT WOULD MAKE US REVISIT:** Services needing to call each other on behalf of a user (token exchange).

**DECISION:** The Gateway's actuator runs on its own management port (8090); port 8080 serves only API routes.
**OPTIONS CONSIDERED:** Permit actuator paths on 8080; separate management port.
**REASON:** ADD §7 keeps actuator internal; a separate port cannot be reached through the public route table.
**TRADE-OFF:** One more port for probes, the Dockerfile healthcheck, and the Prometheus target.
**WHAT WOULD MAKE US REVISIT:** A platform that can only probe the serving port.

**DECISION:** The product read model is a `ProductView` record filled by a JPQL constructor expression; cached list pages use a `ProductPage` record with the same JSON as Spring Data's page DTO.
**OPTIONS CONSIDERED:** Interface projections; caching Spring Data `Page` objects; records.
**REASON:** Interface projections are runtime proxies and `PageImpl` does not deserialize, so neither caches cleanly in Redis; records serialize as plain JSON.
**TRADE-OFF:** Two small DTO types to keep in step with the API.
**WHAT WOULD MAKE US REVISIT:** A separate read store, which the handbook only allows for a justified problem.

**DECISION:** Product cache entries are evicted after the write transaction commits; Redis errors fall back to PostgreSQL.
**OPTIONS CONSIDERED:** `@CacheEvict` around the write; eviction in `afterCommit`.
**REASON:** Evicting after commit means a rolled-back write never evicts and the next read sees committed data.
**TRADE-OFF:** A read that runs between commit and eviction can still return the old value until it is evicted or the 10-minute TTL ends.
**WHAT WOULD MAKE US REVISIT:** Prices that must be exact at every instant.

**DECISION:** Rate limiting keys signed-in requests by JWT subject and anonymous requests by client IP, with `X-Forwarded-For` honoured only from configured trusted proxies; the limiter fails open when Redis is down.
**OPTIONS CONSIDERED:** One limit for everyone; per-route limits; per-client keys with separate anonymous and signed-in limits.
**REASON:** One client cannot slow others, and the ADD §7 numbers keep the k6 plan valid (read load ≥ 50 req/s from one IP is below 100 req/s; order load is ≤ 20 req/s per subject).
**TRADE-OFF:** During a Redis outage there is no rate limiting.
**WHAT WOULD MAKE US REVISIT:** Abuse during Redis outages becoming unacceptable — then fail closed.

**DECISION:** The parent POM binds Failsafe (classes from `target/classes`) and compiles with `-parameters`.
**OPTIONS CONSIDERED:** Per-module plugin configuration; parent configuration.
**REASON:** Without Failsafe, `*IT` tests never ran on `mvn verify`; without `-parameters`, named `@Query` parameters failed — found by `ProductRepositoryIT`. Our parent does not inherit `spring-boot-starter-parent`, which sets both.
**TRADE-OFF:** None for modules without integration tests.
**WHAT WOULD MAKE US REVISIT:** Switching the parent to `spring-boot-starter-parent`.

**DECISION:** The PostgreSQL host port is configurable (`POSTGRES_HOST_PORT`, default 5432) and each service reads `<SERVICE>_DB_PORT`.
**OPTIONS CONSIDERED:** Fixed 5432; configurable port.
**REASON:** A machine with a local PostgreSQL already on 5432 receives `localhost` connections there instead of the Compose database.
**TRADE-OFF:** One more variable to set on such machines.
**WHAT WOULD MAKE US REVISIT:** Running only in containers, where the host port does not matter.

## Startup commands

Infrastructure and platform as in `docs/phases/L0.md`. After pulling L1, recreate Keycloak once so it imports the new audience mappers (steps in the root `README.md`). Then, in separate terminals, with the variables from `deployment/docker/.env` exported:

```sh
mvn -pl platform/config-server spring-boot:run
mvn -pl platform/eureka-server spring-boot:run
mvn -pl platform/api-gateway spring-boot:run      # needs GATEWAY_CLIENT_SECRET
mvn -pl services/product-service spring-boot:run  # needs PRODUCT_DB_PASSWORD (and PRODUCT_DB_PORT if not 5432)
```

## Evidence

Recorded 2026-10-01, JDK 21, Docker Compose infrastructure, Keycloak 26.3 with the L1 realm.

- `mvn -B clean verify`: BUILD SUCCESS on each story branch; integration tests ran against Testcontainers PostgreSQL and Redis.
- Gateway against real Keycloak: anonymous `GET /api/v1/products` → 200 (503 before product-service ran, proving the service token was fetched); `POST /api/v1/products` without token → 401, with `customer-test` → 403; `admin-test` on `/api/v1/inventory/check` and `/api/v1/payments` → 403; a `gateway-service` token used as a user token → 401; `/actuator/health` on 8080 → 404, on 8090 → 200. `gateway-service` token `aud`: product-service, inventory-service, order-service.
- product-service through the Gateway: list page `totalElements 20` with `categoryName`; `GET /api/v1/products/1` → `{"id":1,"name":"Wireless Headphones","price":79.99,"categoryId":1,"categoryName":"Electronics"}`; unknown id → 404 error shape; `size=101` → 400. Direct to `:8081`: no token → 401; `order-service` token detail 200, list 403; `payment-operator` token (no `product-service` audience) → 401.
- Admin writes: create → 201 with `Location: /api/v1/products/21`; update → 200; customer update → 403; unknown category → 400 `Category 999 was not found`; negative price → 400; delete → 204 then read → 404.
- Cache: first read 0.236 s, second 0.046 s; Redis keys `products:item::3` and `products:list::0:20` hold JSON; after an admin `PUT` no `products*` key remains and the next read shows the new price.
- Rate limiting: `customer-test` burst of 150 → 60 × 200, 90 × 429 while `admin-test` still got 200; anonymous burst of 600 → 501 × 200, 99 × 429; responses carry `X-RateLimit-Burst-Capacity: 40`, `X-RateLimit-Replenish-Rate: 20`.
