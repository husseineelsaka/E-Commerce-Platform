## Decisions

**DECISION:** Keycloak issues every token with one public issuer (`KC_HOSTNAME=http://localhost:8180`); services validate that issuer but load signing keys from `KEYCLOAK_JWK_SET_URI` and fetch tokens from `KEYCLOAK_TOKEN_URI`, which point at Keycloak's internal address in Compose and Kubernetes.
**OPTIONS CONSIDERED:** One URL everywhere; separate public issuer and internal URLs.
**REASON:** Containers reach Keycloak as `keycloak:8180`, clients as `localhost:8180`. Without a fixed hostname, a token's `iss` depends on who fetched it and services reject tokens from the other side. Loading keys from the JWKS URL also means no Keycloak call at startup.
**TRADE-OFF:** Two extra variables per service in container deployments; the defaults derive them from the issuer, so host runs are unchanged.
**WHAT WOULD MAKE US REVISIT:** A real domain name for Keycloak reachable from both sides.

**DECISION:** On kind, only the eight applications run in the cluster; PostgreSQL, Kafka, Redis, and Keycloak stay in Docker Compose, and the kind node joins the Compose network.
**OPTIONS CONSIDERED:** Infrastructure as Helm charts in the cluster; infrastructure in Compose.
**REASON:** The handbook's Helm requirement is per application service; one shared infrastructure for Compose and kind keeps the laptop setup light and lets both modes use the same data. Pods reach infrastructure by the same names as in Compose (`postgres`, `kafka:29092`, `redis`, `keycloak:8180`).
**TRADE-OFF:** The kind deployment is not self-contained; a cluster without the Compose network needs managed or in-cluster infrastructure.
**WHAT WOULD MAKE US REVISIT:** Deploying to a shared or cloud cluster.

**DECISION:** Kafka has two listeners: `PLAINTEXT://localhost:9092` for the host and `INTERNAL://kafka:29092` for containers and pods.
**OPTIONS CONSIDERED:** One listener advertised as `localhost`; one advertised as `kafka`; two listeners.
**REASON:** A client receives the advertised address; containers cannot use `localhost:9092`, and tools on the host cannot resolve `kafka`.
**TRADE-OFF:** One more listener to configure.
**WHAT WOULD MAKE US REVISIT:** Running all clients inside one network.

**DECISION:** CI builds all eight images on every pull request and pushes `ghcr.io/<owner>/<app>:<commit sha>` only on pushes to `main`.
**OPTIONS CONSIDERED:** Build only on `main`; build and push on every branch.
**REASON:** Pull requests prove that every Dockerfile still builds; only reviewed code becomes a published image.
**TRADE-OFF:** Pull request CI runs longer (about nine minutes with the integration tests and eight image builds).
**WHAT WOULD MAKE US REVISIT:** CI time limiting how often the team can merge.

**DECISION:** The repository is public, so ArgoCD reads it without credentials.
**OPTIONS CONSIDERED:** A read-only token stored as an ArgoCD repository Secret; a public repository.
**REASON:** No credential to create, rotate, or leak for the demo. The full history was scanned before the change: no real secret was ever committed.
**TRADE-OFF:** Anyone can read the code.
**WHAT WOULD MAKE US REVISIT:** Code or configuration that must stay private.

## Startup commands

```sh
# Whole platform in Docker Compose (only the Gateway on http://localhost:8080)
docker compose -f deployment/docker/docker-compose.yml --env-file deployment/docker/.env up -d --build --wait

# kind: stop the Compose app containers (keep the infrastructure), then deploy the charts
docker compose -f deployment/docker/docker-compose.yml --env-file deployment/docker/.env stop config-server eureka-server api-gateway product-service inventory-service payment-service order-service notification-service
bash deployment/kubernetes/up.sh                     # Gateway on http://localhost:30080

# ArgoCD
kubectl create namespace argocd
kubectl apply -n argocd --server-side -f https://raw.githubusercontent.com/argoproj/argo-cd/v3.5.3/manifests/install.yaml
kubectl apply -f deployment/argocd/applications.yaml
```
