# L6 — G4 (S29)

## Goal

B1 Core (FR-16, S15): `review-service` (port 8086) with its own PostgreSQL database and Flyway. A signed-in customer submits one review per product; anyone reads reviews page by page; Product shows the average rating and review count through an idempotent `ReviewSubmitted` projection. The service has its own Gateway route, Helm chart, CI pipeline, and kind/ArgoCD deployment. This layer also finishes the README.

## Decisions

The B1 design itself (a separate service, Product's read model, sum and count instead of an average, a unique constraint for one review per customer) is in ADD §1–§4. These are the decisions taken while building it.

**DECISION:** An event for a product that Product does not have is recorded in `processed_event` and skipped.
**OPTIONS CONSIDERED:** Let the foreign key reject it (retries, then DLT); check that the product exists on submit with a Feign call to Product.
**REASON:** A review for a missing product is not a failure that retries can fix, so it should not fill the DLT. A Feign call on submit would add a second synchronous dependency and a new client permission for little value (ADD §2).
**TRADE-OFF:** Such a review stays in `review_db` without ever showing on a product page.
**WHAT WOULD MAKE US REVISIT:** The verified-purchase stretch goal, which needs Feign to Order anyway.

**DECISION:** Both review-service and product-service declare the `review-events` topic.
**OPTIONS CONSIDERED:** Only the producer declares it; rely on broker auto-creation.
**REASON:** If Product starts first, its listener subscribes to a missing topic and only sees it after the next metadata refresh, 5 minutes by default. The integration test showed exactly that until Product declared the topic too.
**TRADE-OFF:** The partition count is written in two places.
**WHAT WOULD MAKE US REVISIT:** Topics managed outside the applications (for example by a Kafka operator).

**DECISION:** On an existing Keycloak volume, the new `review-service` audience is added to the `gateway-service` client with Keycloak's admin CLI. `realm-export.json` contains it for new installations.
**OPTIONS CONSIDERED:** Delete the Keycloak volume so the realm is imported again; add the mapper by hand.
**REASON:** Keycloak imports the realm only when it does not exist, so a changed export has no effect on a running volume. Adding one mapper keeps every other piece of Keycloak state.
**TRADE-OFF:** One manual step for environments created before L6 (command below).
**WHAT WOULD MAKE US REVISIT:** A realm managed by a tool that applies changes (for example keycloak-config-cli).

## Commands

```sh
# New environment: init-databases.sh creates review_db and the realm import has the review-service audience.
docker compose -f deployment/docker/docker-compose.yml --env-file deployment/docker/.env up -d --build --wait

# Existing environment (Postgres and Keycloak volumes created before L6), once:
# set REVIEW_DB_PASSWORD in deployment/docker/.env, then
docker exec -e PW="$REVIEW_DB_PASSWORD" docker-postgres-1 sh -c \
  'psql -U postgres -v password="$PW" -c "CREATE ROLE review_owner LOGIN PASSWORD :'"'"'password'"'"'" -c "CREATE DATABASE review_db OWNER review_owner"'
docker exec -e KP="$KEYCLOAK_ADMIN_PASSWORD" docker-keycloak-1 bash -c '
  K=/opt/keycloak/bin/kcadm.sh; $K config credentials --server http://localhost:8180 --realm master --user admin --password "$KP"
  CID=$($K get clients -r ecommerce-platform -q clientId=gateway-service --fields id --format csv --noquotes)
  $K create clients/$CID/protocol-mappers/models -r ecommerce-platform -s name=review-service-audience -s protocol=openid-connect \
    -s protocolMapper=oidc-audience-mapper -s "config.\"included.client.audience\"=review-service" -s "config.\"access.token.claim\"=true"'

# kind with ArgoCD (cluster from L4): load the new image, refresh the Secret, add the Application
kind load docker-image --name ecommerce ecommerce/review-service:local
kubectl -n ecommerce create secret generic ecommerce-secrets --from-env-file=deployment/docker/.env --dry-run=client -o yaml | kubectl apply -f -
kubectl apply -f deployment/argocd/applications.yaml
```

- **Found during L6 (L4 leftovers):**
  - The eight L4 Applications still tracked the L4 branch `capstone-L4/s13-argocd`, so the cluster ran pre-L5 chart values (no `ZIPKIN_ENDPOINT`, no JSON logs). They now track `main`.
  - Rolling all eight at once overloaded the laptop's Docker VM. Scaling every app to 0 and starting them in stages (Config Server, Eureka, Gateway/Product/Review, then the Saga services) brought 9/9 back with 0 restarts.
  - After #31 merged, all nine Applications track `main` and report `Synced` / `Healthy` at revision `4c151d2`.
- **kind DNS after a Docker Desktop restart:** the kind node could reach the internet but could not resolve outside names, so ArgoCD could not fetch from GitHub and pods could not pull images. CoreDNS now has a `github.com` block that forwards to public resolvers. The ArgoCD pods use `imagePullPolicy: IfNotPresent` with the images already on the node. Both are changes to the local cluster only, not to the repository.
- **Outbox polls flooded Zipkin (fixed and verified).**
  - Every outbox poll (500 ms) started its own trace: 169 of the last 200 review-service traces were `task outbox-publisher-job.publish`.
  - `management.observations.enable.tasks.scheduled: false` turns those observations off.
  - After the platform was restarted on Compose with the new Config Server, Zipkin received 0 poll traces from review, order, inventory, and payment.
  - Real traces are intact: an order still CONFIRMED as one trace of 23 spans across all six Saga services, a review still updated product 11 in 0.6 s, and the k6 smoke test passed 130/130 checks, including the review read.
